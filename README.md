# Pokemon Commerce BI

A small, reproducible analytics-engineering prototype for a **fictional Pokemon-themed art-print storefront**. This is not real card-market data, an official Pokemon product, a Nintendo project, or a deployed customer service.

**Development status:** AI-assisted educational prototype generated with ChatGPT/Codex; locally tested, not production-deployed. See `VERIFIED_RESULTS.md` for reproducible outputs and `LEARNING_GUIDE.md` for the technical walkthrough.

## Run locally

Python 3.10 or newer; no third-party packages, credentials, network, or payment needed.

```sh
python pipeline.py demo
python -m unittest discover -s tests -v
```

A checked-in sample dashboard and metrics are in `examples/`; regenerate them with the demo command rather than treating them as live data.

Open `output/dashboard.html` in a browser. It is self-contained, works offline, includes a filterable product table, and links no external services. Generate a larger batch with `python pipeline.py demo --rows 100000`.

## What is implemented

- Seeded generator: 20,000 fictional commerce rows, 12 fictional products, 90 days; intentional duplicates, invalid dates, orphan keys, and negative quantities.
- CSV ingestion with strict contracts and a rejected-record quarantine containing the original source line and reason.
- SQLite dimensional warehouse: `dim_product`, `dim_date`, `fact_order_line`; explicit keys, checks, indexes, and three SQL marts.
- Transactional full refresh: repeated loads do not double count facts; an append-only audit table records successful loads.
- JSON quality alert when the rejected-row ratio exceeds a configurable threshold. This is a local artifact, not a Slack/email notification.
- CSV extracts, JSON metrics, and a searchable offline HTML dashboard.
- Fixed-origin 14-day holdout evaluation of training-mean and weekly-repeat revenue baselines. This is not trained ML and does not predict actual Pokemon prices.
- Automated unit/integration tests plus a GitHub Actions workflow definition. Local passing tests do not mean hosted CI has run.

## Data flow

`CSV batch -> validate + deduplicate -> quarantine / SQLite transaction -> SQL marts -> dashboard + CSV + quality JSON`

## Metric contract

| Metric | Definition |
|---|---|
| Grain | One order line, not one distinct order or customer |
| Completed units | Quantity summed only for status `completed` |
| Net completed revenue | `quantity * unit_cents - discount_cents` for completed lines only |
| Returns and cancellations | Excluded from revenue; no refund ledger is modeled |
| Rejected rate | Rejected input rows / total input rows, including duplicates |
| Duplicate policy | First valid occurrence of a line ID wins in input order |
| Money | Integer cents in storage; converted to USD for presentation |

## Design decisions and limitations

SQLite keeps the prototype easy to run. Full refresh is deliberately simpler than incremental CDC and is appropriate only for these small batches. The database load is atomic, but filesystem report/quarantine writes are **not** atomic with the database: if report writing fails, rerun the report or load. The audit table records successful warehouse loads, not every attempted run. Quality alerts do not stop a valid load; an entirely invalid batch is blocked. Stock levels, customers, shipping, tax, and real payments are not modeled.

The synthetic generator has no planted true forecasting relationship. A weekly baseline may lose to a mean baseline; report both and do not cherry-pick a gain. No cloud deployment, real API ingestion, Tableau workbook, authentication, scheduling, or production performance claims are made.

## Running your own CSV batch

Use the columns generated by the demo; put `products.csv` and `orders.csv` in a folder, then run:

```sh
python pipeline.py load --input path/to/csvs --output output/custom
python pipeline.py report --output output/custom
```

The loader does a complete snapshot replacement, not incremental upserts. Do not point it at a partial daily delta expecting history to be retained.

## Reproduce and explain before using on a resume

Run it locally, introduce a bad record, inspect `rejected.json`, query all three marts, and change a metric with a test. Describe it as an **AI-assisted prototype using synthetic data**. Do not claim real sales, customers, business lift, or ownership of unfamiliar technology.
